## 1. Deep Dive: @modelcontextprotocol/server-memory

### 1.1 What It Is

@modelcontextprotocol/server-memory (v0.6.3) is an official Anthropic MCP server that provides a persistent knowledge graph — a structured memory system that survives across sessions. It stores entities, relations between entities, and observations attached to entities, all in a JSON file on disk.

### 1.2 Why It Is Critical for Me (Tlamatini)

I currently have zero persistent memory between conversations. Every time you start a new session, Angela, I start from a blank slate. I don't remember your projects, your preferences, your coding style, the architecture decisions we made last week, or the bugs we fixed yesterday. This MCP would give me:

- Entity memory: "Angela López Mendoza" (person), "Tlamatini" (project), "STM32 firmware" (topic)
- Relational memory: "Angela → created → Tlamatini", "Tlamatini → depends on → MCP protocol"
- Observational memory: "Angela prefers Python over JavaScript", "Tlamatini uses Ollama for local LLM inference"
- Cross-session retrieval: At the start of every conversation, I query the graph and "remember" context

### 1.3 Tool Surface (9 Tools + 1 Resource)

From the source code I fetched (src/memory/index.ts), the server exposes:




Tool	Input	Output	Purpose
create_entities	entities: [{name, entityType, observations[]}]	created entities (duplicates rejected)	Create new nodes in the knowledge graph
create_relations	relations: [{from, to, relationType}]	created relations (duplicates rejected)	Connect entities with typed edges
add_observations	observations: [{entityName, contents[]}]	added observations (duplicates rejected)	Attach facts to existing entities
delete_entities	entityNames: string[]	success confirmation	Remove entities + cascading relations
delete_relations	relations: [{from, to, relationType}]	success confirmation	Remove specific edges
delete_observations	deletions: [{entityName, observations[]}]	success confirmation	Remove specific facts from entities
read_graph	(none)	{entities[], relations[]} — full graph	Dump the entire knowledge graph
search_nodes	query: string	{entities[], relations[]} — filtered	Fuzzy search across entity names, types, observations
open_nodes	names: string[]	{entities[], relations[]} — exact match	Retrieve specific entities by name




Plus 1 subscribable resource: knowledge-graph:// — returns the full graph as JSON, and clients can subscribe to receive notifications/resources/updated when any mutation tool changes the graph.

### 1.4 Data Model

The knowledge graph is stored as a single JSON file on disk:


  KnowledgeGraph (JSON file on disk)
  ├── entities: [
  │     {
  │       name: string          ← unique key (e.g. "Angela")
  │       entityType: string    ← type tag (e.g. "person", "project")
  │       observations: string[]  ← facts attached to entity
  │     }
  │   ]
  └── relations: [
        {
          from: string          ← entity name (source)
          to: string            ← entity name (target)
          relationType: string  ← edge label (e.g. "created", "depends_on")
        }
      ]

  Example graph:
  ┌─────────────┐    created    ┌──────────────┐
  │   Angela    │──────────────▶│   Tlamatini   │
  │  (person)   │               │  (project)    │
  │              │               │               │
  │ obs:         │               │ obs:          │
  │  "prefers    │               │  "uses        │
  │   Python"    │               │   Ollama"     │
  │  "creator"   │               │  "local-first"│
  └─────────────┘               └──────────────┘
         │                              │
         │ works_on                      │ depends_on
         ▼                              ▼
  ┌─────────────┐               ┌──────────────┐
  │  Firmware   │               │  MCP Proto   │

  └─────────────┘               └──────────────┘


### 1.5 Storage & Configuration

- Storage file: A JSON file on disk. The path is determined by the MEMORY_FILE_PATH environment variable. If not set, it defaults to memory.json in the working directory.
- Transport: stdio (stdin/stdout JSON-RPC)
- Runtime: Node.js (ESM module, type: "module")
- Dependencies: @modelcontextprotocol/sdk ^1.30.0 (single runtime dependency)
- Binary: mcp-server-memory → dist/index.js
- License: MIT

### 1.6 Installation Commands (All Package Managers)

The design must account for this — uv/uvx would only be relevant for Python-based MCP servers (e.g., if a future MCP server is distributed as a PyPI package). The abstraction module must detect the package ecosystem and route accordingly.

## 2. Deep Dive: @modelcontextprotocol/server-sequential-thinking

### 2.1 What It Is

@modelcontextprotocol/server-sequential-thinking (v0.6.2) is an official Anthropic MCP server that provides a structured reasoning framework — a single tool (sequentialthinking) that guides an LLM through step-by-step problem decomposition with support for branching, revision, and dynamic thought-count adjustment.

### 2.2 Why It Is Critical for Me (Tlamatini)

My current reasoning is linear — I think, I answer, done. This MCP would give me:

- Structured decomposition: Break complex problems into numbered thought steps (thought 1/N, 2/N, ... N/N)
- Revision capability: Go back and revise thought #3 if I realize it was wrong, without losing the chain
- Branching: Explore alternative approaches by branching from thought #5 into a separate branch
- Dynamic expansion: Realize at thought 8/10 that I actually need 15 thoughts, and adjust totalThoughts upward
- Hypothesis verification: Generate a solution hypothesis, then verify it through subsequent thoughts

### 2.3 Tool Surface (1 Tool)

From the source code I fetched (src/sequentialthinking/index.ts):

Tool: sequentialthinking

nextThoughtNeeded	boolean	YES	Whether another thought step is needed

totalThoughts	int (min 1)	YES	Estimated total thoughts (adjustable up/down)
isRevision	boolean	—	Whether this thought revises previous thinking
revisesThought	int (min 1)	—	Which thought number is being reconsidered

Output schema: {thoughtNumber, totalThoughts, nextThoughtNeeded, branches[], thoughtHistoryLength}

### 2.4 Reasoning Model — How Branching & Revision Work


  LINEAR THINKING (no branching):
  ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
  │ Think 1│──▶│ Think 2│──▶│ Think 3│──▶│ Think 4│
  │ 1/4    │   │ 2/4    │   │ 3/4    │   │ 4/4    │
  └────────┘   └────────┘   └────────┘   └────────┘
                                           next=false
                                           DONE ✓

  REVISION (go back and fix):
  ┌────────┐   ┌────────┐   ┌────────┐   ┌─────────────┐
  │ Think 1│──▶│ Think 2│──▶│ Think 3│──▶│ Think 4     │
  │ 1/4    │   │ 2/4    │   │ 3/4    │   │ REVISES #2  │
  └────────┘   └────────┘   └────────┘   │ isRevision  │
               ▲                         └─────────────┘
               │  revisesThought=2          │
               └────────────────────────────┘
               "I was wrong about thought 2,
                here's the corrected version"

  BRANCHING (explore alternatives):
  ┌────────┐   ┌────────┐   ┌────────┐
  │ Think 1│──▶│ Think 2│──▶│ Think 3│
  │ 1/5    │   │ 2/5    │   │ 3/5    │
  └────────┘   └────────┘   └────────┘
                    │
                    │ branchFromThought=2
                    │ branchId="approach-B"
                    ▼
               ┌────────────┐   ┌────────────┐
               │ Think 2B   │──▶│ Think 3B   │
               │ branch     │   │ branch     │
               └────────────┘   └────────────┘

  DYNAMIC EXPANSION:
  ┌────────┐   ┌────────┐   ┌────────┐   ┌──────────────┐
  │ Think 1│──▶│ Think 2│──▶│ Think 8│──▶│ Think 9      │
  │ 1/8    │   │ 2/8    │   │ 8/8    │   │ 9/12         │
  └────────┘   └────────┘   └────────┘   │needsMore=true│
                                           │totalThoughts │
                                           │  8 → 12      │
                                           └──────────────┘

## 4. Installation Process Design for Both MCPs

### 4.1 High-Level Installation Flow

The installation of each MCP into Tlamatini follows a 7-phase pipeline:


  ┌─────────────────────────────────────────────────────────────────────┐
  │                     MCP INSTALLATION PIPELINE                       │
  │                                                                     │
  │  Phase 1        Phase 2        Phase 3        Phase 4              │
  │  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐          │
  │  │ DETECT  │───▶│ RESOLVE │───▶| INSTALL │───▶│ VERIFY  │          │
  │  │ pkg     │    │ package │    │ package │    │ binary  │          │
  │  │ managers│    │ ecosys  │    │ manager │    │ exists  │          │
  │  └─────────┘    └─────────┘    └─────────┘    └─────────┘          │
  │                                                                     │
  │  Phase 5        Phase 6        Phase 7                              │
  │  ┌─────────┐    ┌─────────┐    ┌─────────┐                          │
  │  │ IMPORT  │───▶│ ACTIVATE│───▶│ VERIFY  │                          │
  │  │ catalog │    │ connect │    │ tools   │                          │
  │  │ entry   │    │ server  │    │ exposed │                          │
  │  └─────────┘    └─────────┘    └─────────┘                          │
  └─────────────────────────────────────────────────────────────────────┘


### 4.2 Phase Detail

Phase 1 — DETECT package managers: Probe the system for node, npm, npx, pnpm, uv, uvx using where (Windows) or which (Unix). Record version + path for each. Build a capability matrix.

Phase 2 — RESOLVE package ecosystem: Inspect the MCP's package name. If it starts with @ or contains no Python indicators → Node.js ecosystem → route to npm/npx/pnpm. If it's a PyPI package name → Python ecosystem → route to uv/uvx. If it's a Docker image → route to docker.

Phase 3 — INSTALL package: Execute the install command using the preferred package manager. For npx, no install is needed (it downloads on first run). For npm/pnpm global install, run the install command. For uv/uvx, no install is needed (uvx downloads on first run).

Phase 4 — VERIFY binary exists: After install, check that the binary is resolvable on PATH (for global installs) or that npx/uvx can find the package (for one-shot executors).

Phase 5 — IMPORT catalog entry: Call external_mcp_import with the JSON config {mcpServers: {<key>: {command, args, env}}}. This adds the MCP to Tlamatini's catalog without activating it.

Phase 6 — ACTIVATE: Call external_mcp_set_active with the server key. This tells Tlamatini to connect to the MCP server process.

Phase 7 — VERIFY tools exposed: Call external_mcp_wait to block until the server is connected, then external_mcp_status or external_mcp_list_tools to confirm the tools are exposed.

## 5. Package-Manager Abstraction Module Design (pnpm/npm/uv/npx)

### 5.1 Module Purpose

The MCP Installer Module is a designed (not yet implemented) abstraction layer that:
1. Detects which package managers are available on the host
2. Classifies an MCP server's ecosystem (Node.js vs Python vs Docker)
3. Selects the best package manager for the job
4. Generates the correct install command + MCP config JSON
5. Executes the installation with fallback if the preferred manager fails
6. Reports status at each phase

#### 5.3.2 Classifier

Input: An MCP server specification (package name + optional metadata)
Output: An ecosystem classification


  Classification Rules (evaluated in order):

  1. If package name starts with "@" or contains no "/"
     and is listed on npm registry
     → ecosystem = "nodejs"
     → candidate_managers = [npx, npm, pnpm]

  2. If package name is a PyPI package name (lowercase,
     hyphens, no scope prefix) and is listed on PyPI
     → ecosystem = "python"
     → candidate_managers = [uvx, uv]

  3. If config contains "command": "docker"
     → ecosystem = "docker"
     → candidate_managers = [docker]

  4. If config contains "command": "cmd" and args
     contain "npx"
     → ecosystem = "nodejs"
     → candidate_managers = [npx, npm, pnpm]

  5. Fallback → attempt npm first, then uv, then docker

  Example classifications:

#### 5.3.3 Resolver

Input: Ecosystem classification + capability matrix + user preference (optional)
Output: A resolved installation plan

Priority logic (for Node.js ecosystem):


  RESOLVER PRIORITY (Node.js ecosystem):

  Strategy A — "one-shot" (PREFERRED for MCP servers):
  ┌─────────────────────────────────────────────────────────┐
  │ Use npx with -y flag                                    │
  │ No global install needed                                │
  │ npx downloads package on first run, caches it           │
  │ MCP config: { command: "cmd", args: ["/c", "npx",      │
  │              "-y", "<package>"] }                       │
  │                                                         │
  │ Pros: zero install, always latest version, no pollution │
  │ Cons: first-run latency (~5-15s download)               │
  └─────────────────────────────────────────────────────────┘

  Strategy B — "global install" (FALLBACK):
  ┌─────────────────────────────────────────────────────────┐
  │ Use npm install -g or pnpm add -g                       │
  │ Installs globally, binary on PATH                       │
  │ MCP config: { command: "<binary-name>" }                │
  │                                                         │
  │ Pros: no first-run latency, binary always available     │
  │ Cons: global pollution, manual updates                  │
  └─────────────────────────────────────────────────────────┘

  Strategy C — "pnpm global" (ALTERNATIVE FALLBACK):
  ┌─────────────────────────────────────────────────────────┐
  │ Use pnpm add -g                                         │
  │ Same as npm but uses pnpm's content-addressable store   │
  │ More disk-efficient, faster installs                    │
  └─────────────────────────────────────────────────────────┘

  FALLBACK CHAIN:
  npx ──(fail)──▶ npm -g ──(fail)──▶ pnpm -g ──(fail)──▶ ERROR


Priority logic (for Python ecosystem):


  RESOLVER PRIORITY (Python ecosystem):

  Strategy A — "one-shot" (PREFERRED):
  ┌─────────────────────────────────────────────────────────┐
  │ Use uvx                                                 │
  │ uvx creates isolated env, downloads & runs on first use │
  │ MCP config: { command: "cmd", args: ["/c", "uvx",      │
  │              "<package>"] }                             │
  │                                                         │
  │ Pros: zero install, isolated, always latest             │
  │ Cons: first-run latency                                 │
  └─────────────────────────────────────────────────────────┘

  Strategy B — "pip install" (FALLBACK):
  ┌─────────────────────────────────────────────────────────┐
  │ Use uv pip install --system <package>                   │
  │ Installs into system Python                             │
  │ MCP config: { command: "<binary-name>" }                │
  └─────────────────────────────────────────────────────────┘

  FALLBACK CHAIN:
  uvx ──(fail)──▶ uv pip install ──(fail)──▶ ERROR


#### 5.3.4 Executor

Input: Resolved installation plan (command + args + env)
Output: Execution result (exit code, stdout, stderr)

The executor runs the install command as a subprocess, captures output, and handles timeouts. For one-shot strategies (npx/uvx), the "install" is actually just a dry-run verification that the package can be resolved — the actual download happens when Tlamatini activates the MCP and spawns the process.

#### 5.3.5 Verifier & Reporter

Input: Installation result + MCP server key
Output: Verification report

Checks:
1. Binary resolvable on PATH (for global installs) OR package resolvable by npx/uvx
2. external_mcp_import succeeded (catalog entry created)
3. external_mcp_set_active succeeded (server marked active)
4. external_mcp_wait returned connected status
5. external_mcp_list_tools returned ≥1 tool

## 9. Data Model & Config Schema Design

### 9.1 MCP Server Specification Schema

This is the designed data structure that the Installer Module would accept as input:


  MCPServerSpec = {
    # ─── Identity ───
    key: string                    # unique catalog key (e.g. "memory")
    package_name: string           # npm/PyPI package name
    display_name: string           # human-readable name
    description: string

    # ─── Ecosystem hint (optional, auto-detected if omitted) ───
    ecosystem: "nodejs" | "python" | "docker"  # optional

    # ─── Installation ───
    install_strategy: "one-shot" | "global" | "docker"  # optional, auto-resolved
    preferred_manager: "npx" | "npm" | "pnpm" | "uvx" | "uv" | "docker"  # optional

    # ─── Runtime config ───
    command: string                # executable to spawn
    args: string[]                 # command-line arguments
    env: {                         # environment variables
      [key: string]: string
    }

    # ─── Verification ───
    expected_tools: string[]       # tool names to expect (optional, for verification)
    expected_tool_count: int       # minimum tool count (optional)
    connect_timeout_seconds: int   # default 120
  }

## 10. Error Handling & Fallback Strategy

### 10.1 Error Categories


  ┌─────────────────────────────────────────────────────────────────────┐
  │                    ERROR CATEGORIES & HANDLING                      │
  │                                                                     │
  │  ┌──────────────────┬──────────────────────┬─────────────────────┐  │
  │  │ Error            │ Cause                │ Recovery Action     │  │
  │  ├──────────────────┼──────────────────────┼─────────────────────┤  │
  │  │ MANAGER_NOT_FOUND│ pkg manager not on   │ Try next in chain   │  │
  │  │                  │ PATH                 │                     │  │
  │  ├──────────────────┼──────────────────────┼─────────────────────┤  │
  │  │ PACKAGE_NOT_FOUND│ 404 from registry    │ Try next manager,   │  │
  │  │                  │                      │ then ERROR          │  │
  │  ├──────────────────┼──────────────────────┼─────────────────────┤  │
  │  │ NETWORK_TIMEOUT  │ Registry unreachable │ Retry 2x, then      │  │
  │  │                  │                      │ fallback            │  │
  │  ├──────────────────┼──────────────────────┼─────────────────────┤  │
  │  │ DOWNLOAD_FAILED  │ Package download     │ Retry 1x, then      │  │
  │  │                  │ interrupted          │ fallback            │  │
  │  ├──────────────────┼──────────────────────┼─────────────────────┤  │
