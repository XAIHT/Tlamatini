# Tlamatini — Agent Descriptions

This file is the **authoritative source of human-readable descriptions** for every workflow agent shown in the Agentic Control Panel sidebar of Tlamatini.

The Django view `agent.views.agentic_control_panel` parses the table rows under `## Workflow Agents` below and injects the `Description` column into the page as `agent_purpose_map` JSON. The frontend (`acp-canvas-core.js`) reads that JSON and uses the text as the **hover tooltip** over each sidebar agent and as the **Description** dialog body when the user right-clicks an agent on the canvas.

Editing a row's `Description` cell here changes both:
- the documentation read by humans, AND
- the live UI text displayed to end users.

The lookup is case- and punctuation-insensitive: the key for each row is `re.sub(r'[^a-z0-9]+', '', name.lower())`. So "Kyber-KeyGen", "Kyber KeyGen", and "kyberkeygen" all resolve to the same description.

Descriptions are written for **non-expert readers** — when in doubt, prefer the longer, friendlier phrasing over a terse one-liner. A user who has never seen the agent before should be able to understand **what it does, when to use it, and what its main inputs/outputs are** from a single tooltip read.

## Workflow Agents

> **Note — the canvas PDF reader is not an agent.** Opening a PDF in the *chat* canvas and turning it into context (2026-09-16) is a page feature, not a workflow agent, so it has no row in this file: see [docs/pdf-canvas.md](docs/pdf-canvas.md). It does reuse the **Image-Interpreter** agent below for its optional image analysis, and it is distinct from **File-Extractor** (which extracts raw text from a PDF you name) and **PDFer** (which *creates* PDFs).

The visual workflow designer ships with **89 agent types**, grouped below by their role in a flow. Drag any of them onto the canvas, wire connections between them, and press *Start* — the agents run as separate, log-emitting processes that talk to each other through their `config.yaml` files.

### Control Agents

These agents shape the lifecycle of a flow: when it begins, when it ends, and what gets cleaned up afterward.

| Agent | Description |
|-------|-------------|
| **Starter** | The entry point of every flow. When the user clicks *Start*, the Starter is the first agent that runs; its only job is to launch the agents listed in its `target_agents`. Think of it as the green "Play" button of the canvas — it does no real work itself, it simply kicks off the chain. |
| **Ender** | Terminates a flow gracefully. Kills every agent listed in its `target_agents`, then launches anything wired into its `output_agents` (typically a FlowBacker for backups, followed by Cleaners that wipe transient files). Use Ender at the bottom of every flow that should shut down on its own. |
| **Stopper** | A surgical "kill the noisy neighbor" agent. It watches the logs of one or more `source_agents` and, when a configured pattern appears (e.g. `FAILED`, `out of memory`), terminates exactly those source agents — without bringing the whole flow down. Stopper does NOT start downstream agents; it is purely a controlled-shutdown tool. |
| **Cleaner** | The post-mortem janitor. After an Ender or FlowBacker completes, the Cleaner deletes the `.log` and `.pid` files of the agents it was wired to, returning the session pool to a clean slate. It is the only agent that should be wired AFTER Ender. |
| **Sleeper** | A timed pause. Waits for a configured number of milliseconds, then starts everything in `target_agents`. Useful for rate-limiting polling loops, giving an external service time to settle, or building "every N seconds" cycles when paired with a Raiser. |
| **Croner** | A clock-driven trigger. Wakes up at the configured `HH:MM` every day and starts its `target_agents`. Good for nightly backups, scheduled reports, or any "run this every day at 3 AM" flow. Pair it with Gatewayer if you also want event-driven triggers in the same flow. |

### Routing Agents

These agents decide WHERE the flow goes next based on what they observe in upstream logs or user input.

| Agent | Description |
|-------|-------------|
| **Raiser** | An event-driven launcher. Continuously watches the logs of its `source_agents` for a configured `pattern`. When the pattern appears, it fires every agent in `target_agents`. Raiser is the bread-and-butter bridge between *passive* monitoring agents and *active* action agents — anywhere you want "when X happens, do Y", a Raiser is the right answer. |
| **Forker** | An automatic A/B router. Watches its source agents for two distinct sets of patterns (`pattern_a` and `pattern_b`); whichever set matches first determines which path the flow takes next (`target_agents_a` or `target_agents_b`). Use it whenever a single upstream signal can mean two different things and each meaning has its own downstream chain. |
| **Asker** | An interactive A/B chooser. When it runs, it pops a dialog in the chat UI asking the user to pick Path A or Path B (with optional captions like "Approve" / "Reject"). The chosen path's `target_agents` are launched and the rejected path is left untouched. Has a 5-minute timeout. Perfect for human-in-the-loop approvals or a/b experiments. |
| **Counter** | A persistent tally with threshold-based routing. Each time it runs it increments a stored counter and compares it against a `threshold_value`. If the counter is below the threshold it fires `target_agents_l` (less); if it has reached or passed the threshold it fires `target_agents_g` (greater). The count survives flow restarts via reanim files, so it can drive "do this 5 times then do that" loops. |

### Logic Gates

These agents hold the flow until specific upstream conditions are met — they are pure synchronization primitives.

| Agent | Description |
|-------|-------------|
| **AND** | A two-input AND gate. Fires its `target_agents` only when BOTH `source_1` AND `source_2` have produced their respective patterns. The match is *latched*: once a source matches, that side stays satisfied until the gate fires. Use it to require two parallel branches to both succeed before continuing. |
| **OR** | A two-input OR gate. Fires its `target_agents` when EITHER `source_1` OR `source_2` produces its pattern, whichever happens first. Use it for "the first one wins" patterns, e.g. continue as soon as either of two redundant data sources finishes. |
| **Barrier** | An N-input barrier (a generalized AND). Waits until ALL configured `source_agents` have started, then fires its `target_agents`. The first source to arrive becomes the polling watcher; every subsequent arrival drops a flag file and the gate releases when all flags are present. Designed for fan-in synchronization across many parallel branches without any race conditions. |

### Action Agents

These are the agents that *do real work* — running commands, hitting APIs, producing files, calling LLMs, automating the desktop.

| Agent | Description |
|-------|-------------|
| **Executer** | Runs an arbitrary shell command and triggers its `target_agents` when the command finishes. The command's stdout and stderr are captured to its log file. The simplest, most flexible "do something on this machine" agent — anywhere you would have typed a command into a terminal, an Executer can do it for you. **Preferred over Keyboarder / Mouser whenever a command or build step needs to run; never type a command into a terminal window through Keyboarder — give it to Executer instead.** |
| **Pythonxer** | Runs an inline Python script (provided as a YAML string) behind a STRICT correctness gate: it first `compile()`-parses the script (an unparsable script is refused, never run) and then validates it with Ruff — when `ruff_blocking` is true (the default) any Ruff finding aborts execution with the findings logged. The script can use any installed package. **Downstream agents are ALWAYS triggered afterwards — no matter what (success, a gate refusal, or a runtime failure)** — so Pythonxer never dead-ends a flow; the exit code (0/non-zero) drives only the LED and the Multi-Turn fix-and-retry loop. Wire a downstream agent to inspect the result/log if a step must only proceed on success. An optional `execute_forked_window` flag opens the script in a new console for live stdout. Great for ad-hoc data wrangling, custom logic, or anything you'd write a one-off `.py` file for. **Preferred over Keyboarder / Mouser for code execution and computed-content generation; never drive Keyboarder to type Python into IDLE or an editor — feed the code to Pythonxer instead.** |
| **Sqler** | Executes a Python block against a Microsoft SQL Server instance using `pyodbc`. The script receives `cursor` and `conn` as injected globals so you can write `cursor.execute("SELECT ...")` directly. Triggers downstream agents when the SQL completes successfully. Use it for ETL steps, schema checks, data exports, or anything that needs a real SQL session. |
| **Mongoxer** | Executes a Python block against a MongoDB database using `pymongo`. The script receives a pre-connected `db` object so you can write `db.users.find({...})` directly. Triggers downstream agents on success. The MongoDB twin of Sqler — perfect for document-store reads, writes, and aggregations inside a flow. |
| **Crawler** | A developer-oriented web crawler with built-in LLM analysis. Fetches a URL via HTTP GET and captures **raw content by default** (full HTML, inline JS, CSS, headers, JSON-LD, data-* attributes, the lot) or plain text on demand. Optionally walks all links on the same domain or every link found. The result is sent to an Ollama model with a developer-centric system prompt that produces a structured analysis. Outstanding for security audits, competitive analysis, or any "tell me what this page actually does" task. |
| **Googler** | Performs resilient two-tier indexed-web search, then either extracts readable text/raw HTML from the top results or returns only the hit URLs. Tier 0 uses plain `urllib` against four server-rendered routes (DuckDuckGo HTML, Bing, DuckDuckGo Lite, Mojeek), avoiding browser fingerprints and stale CSS selectors. If those return nothing, Tier 1 uses visible installed Chrome (bundled Chromium fallback) across seven direct-results routes with bounded jittered retries and answer-route logging. Its structured dork builder normalizes exact phrases, exclusions, dates, ranges, proximity, title/URL/text/anchor filters, discovery operators, and parenthesized uppercase-`OR` groups for multiple sites or file types. Presets cover books, lawful public/open books, papers, manuals, documents, slides, sheets, and directory listings; aliases such as `ebook`, `docs`, `code`, and `data` expand automatically, while explicit fields override preset defaults. Use `content_mode: links_only` for PDF/EPUB/file hunts, then pass URLs to Apirer/File-Extractor/File-Interpreter. Advanced date/proximity/range operators are Google-specific and may broaden on fallback engines; pin `engines: [google]` when exact semantics matter (and to skip Tier 0). The direct Multi-Turn `googler` tool accepts manual operators in `query`; structured fields are the visual/pool surface. Googler finds public indexed URLs only, never bypasses access controls, and leaves copyright, licensing, authorization, and use to the operator. |
| **Playwrighter** | A scripted, interactive browser-automation agent built on Playwright (Chromium/Firefox/WebKit). Where Crawler does a static one-shot HTTP fetch and Googler only searches, Playwrighter drives a REAL browser through an ordered list of steps — navigate, fill forms, click, press keys, wait for elements, extract text/attributes, screenshot, assert, download — so it can log into a site, submit a multi-step form, click through a wizard, scrape a JavaScript-rendered single-page-app behind a login, or run an end-to-end UI check. Set `headless: false` to watch it drive, and `hold_open_seconds: N` (alias `hold_open_ms`) to keep the browser visible for N seconds after the last step before it closes (the "wait before closing so I can see it" knob); use `storage_state_in`/`storage_state_out` to carry a logged-in session between runs. It writes an `INI_SECTION_PLAYWRIGHTER` block (`status`, `assert_result`, extracted values) so a downstream Forker can branch on pass/fail and Parametrizer can pipe scraped data onward, and always triggers `target_agents` (success or failure). The visual-canvas counterpart of the `chat_agent_playwrighter` Multi-Turn tool. |
| **Apirer** | An HTTP/REST API client agent. Performs a configurable GET / POST / PUT / DELETE request with arbitrary headers, body, and timeout, then logs the response status, body and round-trip latency in milliseconds. Authorization headers are masked in the log for security. Triggers downstream agents regardless of HTTP outcome (so retries and error branches are wired downstream, not inside the agent). |
| **Kalier** | Tlamatini's bridge to **Kali Linux** offensive-security tooling, built on the MCP-Kali-Server (https://www.kali.org/tools/mcp-kali-server/). On trigger it POSTs to the MCP-Kali-Server Flask API (`server.py`) running on a Kali box and runs ONE capability selected by its `action` field: `nmap` (port/service scan), `gobuster` / `dirb` (web content & directory busting), `nikto` (web-server scan), `sqlmap` (SQL-injection testing), `wpscan` (WordPress scan), `enum4linux` (SMB/Samba enumeration), `hydra` (credential brute-force), `john` (hash cracking), `metasploit` (run a module), `command` (any shell command on the Kali box), or `health` (probe the API server and which tools are installed). It captures the tool's stdout/stderr into an `INI_SECTION_KALIER` block (`action`, `endpoint`, `subject`, `return_code`, `success`, `timed_out`, `server_url`) so a downstream Forker can branch on `{success}` / `{return_code}` and Parametrizer can pipe the output onward; it ALWAYS triggers `target_agents` (success or failure). Point `server_url` at the running API server (default `http://127.0.0.1:5000`; for a remote Kali box use an SSH tunnel `ssh -L 5000:localhost:5000 user@KALI_IP`, or set it to `http://<KALI_LAN_IP>:5000`). In **chat (Multi-Turn)** you never repeat the URL — Tlamatini is the embedded MCP-Kali-Server client and auto-injects the **`kali_server_url`** you set once in **Config ▸ URLs** as the default `server_url` on every `chat_agent_kalier` run (the LLM may still pass `server_url=` to override for a one-off box); on the canvas you set `server_url` in this node's dialog. Implemented self-contained with the Python stdlib (`urllib`), so it needs no extra packages in the agent pool. **Authorized use only — run Kalier ONLY against systems you own or are explicitly authorized to test (engagement, lab, CTF).** The visual-canvas counterpart of the `chat_agent_kalier` Multi-Turn tool. |
| **Discoverer** | Tlamatini's bridge to the **ProjectDiscovery** security-tool suite (https://github.com/projectdiscovery) for recon, attack-surface mapping and vulnerability discovery. On trigger it runs ONE tool selected by its `tool` field: `subfinder` (passive subdomain enumeration), `httpx` (HTTP probe & fingerprint), `naabu` (port scan), `katana` (crawler/spider), `nuclei` (template vulnerability scan), or `cvemap` (CVE search — runs ProjectDiscovery's `vulnx`, since cvemap's own API was retired Aug 2025; filters `cvemap_severity`/`cvemap_product`/`cvemap_limit`) — plus the meta actions `bootstrap` / `validate` / `update_templates` / `list_tools`. It invokes each tool's own CLI DIRECTLY (no MCP server) like Kalier/ESP32er/Arduiner, self-contained on the Python stdlib. **ZERO-CONFIG**: on the first call it downloads a PRIVATE Go compiler into `<install_dir>/Go` and `go install`s the requested tool into `<install_dir>/Go/bin-tools` — no system Go, no PATH change (the first run is slow, then cached). It captures the tool's stdout + saved JSON into an `INI_SECTION_DISCOVERER` block (`tool`, `target`, `returncode`, `success`, `findings_count`, `json_path`, `pdcp_used`, `stage`) so a downstream Forker can branch on `{success}` / `{findings_count}` and Parametrizer can pipe results onward; it ALWAYS triggers `target_agents` (success or failure). The `pdcp_api_key` (ProjectDiscovery Cloud Platform) is OPTIONAL for every tool (it lifts cvemap's rate limit and enables nuclei's AI/cloud upload); subfinder reads its own `provider-config.yaml` for OSINT source keys. Set the PDCP key once in Config ▸ Access Keys Wizard ▸ 'Security Recon (ProjectDiscovery)' (auto-injected on every run; redacted from `.flw` exports and by `regen_secrets.py` before a push). `naabu` defaults to a CONNECT scan on Windows (no Npcap/admin needed); a fail-safe preflight REFUSES rather than mis-scan. **Authorized targets only** — subfinder/cvemap are passive, but httpx/naabu/katana/nuclei actively touch the target. The visual-canvas counterpart of the `chat_agent_discoverer` Multi-Turn tool. |
| **Nmapper** | Tlamatini's LOCAL, **USE-ONLY** nmap bridge for pentesters / CTF recon. It runs a real `nmap` the user installed themselves — it **NEVER bundles or redistributes nmap** (nmap's NPSL forbids embedding it in a product without a paid OEM licence), so a scan only ever uses an nmap the user already has (resolved from PATH → `C:\Program Files\Nmap\nmap.exe` → a `%LOCALAPPDATA%\Tlamatini\nmap` copy). If none is found it REFUSES gracefully with install guidance, and `action='install'` (or `auto_install`) downloads + launches the OFFICIAL FREE nmap self-installer from nmap.org — the user's own download + admin install, which also brings Npcap. The DEFAULT is an UNPRIVILEGED TCP CONNECT SCAN (`-sT`) that needs NO Npcap and NO admin, so a fresh install scans immediately; raw-packet features (SYN `-sS` / OS-detect `-O` / UDP `-sU`) degrade gracefully on Windows without Npcap (auto-downgrade to a connect scan + a warning, never a crash). Pick ONE capability with `action`: `quick` (`-sT -sV -sC -Pn -T4 --top-ports 1000`, the CTF opener) / `full` (all 65535 TCP ports) / `top_ports` / `version` / `scripts` (targeted NSE) / `host_discovery` / `udp` / `custom` (safe base + validated `custom_args`; shell metacharacters rejected) / `validate` / `install`. It parses nmap's `-oX` XML + keeps the `-oN` report and emits an `INI_SECTION_NMAPPER` block (`action`, `target`, `scan_technique`, `ports`, `return_code`, `success`, `hosts_up`, `open_ports`, `npcap_present`, `xml_path`, `output_path`, `stage`) so a downstream Forker can branch on `{success}` / `{open_ports}`; it ALWAYS triggers `target_agents`. Direct-CLI sibling of Kalier/Discoverer, self-contained on the Python stdlib. **Distinct from Kalier** (a REMOTE Kali box via MCP-Kali-Server) and **Discoverer** (the ProjectDiscovery suite): Nmapper is the instant, zero-install LOCAL nmap. **AUTHORIZED TARGETS ONLY** — only scan hosts you own or are explicitly authorized to test (e.g. scanme.nmap.org). The visual-canvas counterpart of the `chat_agent_nmapper` Multi-Turn tool. |
| **Unrealer** | Drives an Unreal Engine 5 editor instance through the Unreal MCP plugin's TCP protocol (default 127.0.0.1:55557 — the plugin must already be running inside UE5; the agent does not start the engine). Sends one JSON command per execution (`{"type": <command>, "params": {...}}`) and captures the full Unreal response into an `INI_SECTION_UNREALER` block so Parametrizer can route specific fields into downstream agents. Forwards any command the connected plugin build exposes; the extended Unreal MCP surface is 53 commands across nine categories: actor manipulation incl. `focus_viewport` and `take_screenshot` (observe-your-change), Blueprint creation/editing incl. `set_pawn_properties`, Blueprint node-graph wiring incl. `find_blueprint_nodes`, input mappings, UMG widget building, **system** (`execute_python` — the universal in-editor escape hatch — plus `execute_console_command`, `get_class_info`, `list_assets`), **level/world** (`open_level` / `save_current_level` / `save_all` / `new_level` / `get_current_level`), **asset** (`import_asset` / `duplicate_asset` / `rename_asset` / `delete_asset` / `save_asset` / `create_folder`), and **material** (`create_material` / `create_material_instance` / `set_material_parameter` / `assign_material`). Headless build/cook/test is out of scope (that needs UnrealEditor-Cmd, not this editor socket). The visual-canvas counterpart of the wrapped `chat_agent_unrealer` Multi-Turn tool — same command surface, same response shape, fully unattended and chainable through Parametrizer. The recommended plugin to install is Tlamatini's own extended Unreal MCP fork — the Unreal Engine MCP modified specifically for this system — at https://github.com/XAIHT/XaihtUnrealEngineMCP.git (built on the upstream https://github.com/chongdashu/unreal-mcp; it ships the full 53-command surface). That same repo ALSO ships `scaffold_unreal_project.py`, which scaffolds a ready-to-open, ready-to-build **UE 5.8** C++ project (UnrealMCP pre-wired, **Visual Studio 2026** solution generated) from just a project name + directory — driven by the Catalog-of-Prompts entry `prompt-106`. |
| **Blenderer** | Drives a Blender instance through the OFFICIAL Blender MCP add-on's TCP socket (default localhost:9876 — the add-on must already be running inside Blender with "Online access" enabled and the server started; the agent does not launch Blender). Unlike Unreal's verb-dispatch protocol, the Blender MCP wire format is a CODE-EXECUTION protocol — each run sends `{"type":"execute","code":<python>,"strict_json":<bool>}` (NUL-framed) and Blender runs that Python (which assigns a `result` dict) — so Blenderer exposes a RICH ACTION CATALOG selected by its `command` field instead of forcing hand-written Python for every task: PASSTHROUGH `execute_code` (run arbitrary `bpy` Python — the universal escape hatch); READ-ONLY `ping` / `scene_info` / `get_objects` / `get_object_detail` / `blendfile_summary`; and MUTATING/OUTPUT `create_object` (cube/sphere/cylinder/cone/plane/monkey/torus), `delete_object`, `set_material` (Principled base colour), `screenshot`, and `render` (file outputs default under Tlamatini's Temp directory). It captures the full Blender response into an `INI_SECTION_BLENDERER` block (`host`, `port`, `command`, `status`, `error`, `response_body`) so a downstream Forker can branch on `{status}` and Parametrizer can pipe fields onward; it ALWAYS triggers `target_agents` (success or failure). Implemented self-contained with the Python stdlib (raw NUL-byte-framed socket), so the agent pool needs no extra packages. Because Tlamatini speaks the add-on socket DIRECTLY (no separate `blmcp` MCP-server bridge and no external LLM client), it is a drop-in, far more integrated alternative to the bare chat client blender.org recommends — with the full Tlamatini canvas, Multi-Turn, Exec Report and Parametrizer pipelines on top. The visual-canvas counterpart of the wrapped `chat_agent_blenderer` Multi-Turn tool. |
| **STM32er** | Tlamatini's STM32 firmware agent — it programs the **WHOLE ST 32-bit line, from the Blue Pill (STM32F103) up through F7 / G0 / G4 / L0..L5 / H7 / U5 / WB**, via **two backends** chosen by `stm32_backend` (default `auto`). **(1) PlatformIO backend** (the broad, zero-config path): drives PlatformIO Core's `ststm32` platform **directly** (the ESP32er pattern — no MCP server), so a `board` (e.g. `bluepill_f103c8`, `nucleo_h743zi`, `disco_f407vg`) fixes the memory map/linker and one backend builds & flashes ~1000 STM32 boards; it auto-installs PlatformIO Core into the SHARED per-user dir ESP32er also uses, and `framework` defaults to `arduino` (stm32duino — a board-agnostic blink works everywhere) or `stm32cube` for bare HAL. **(2) Template-MCP backend** (STM32F407VG + rich serial/SWD HIL): drives the **STM32 Template Project MCP** (https://github.com/XAIHT/STM32TemplateProjectMCP) — a self-contained scaffold + MCP server that lets a flow **scaffold → author → build → flash → observe** STM32F4 firmware programmatically, with **no STM32CubeIDE GUI**, using the GCC / CubeProgrammer / HAL toolchain bundled inside STM32CubeIDE. Under `auto`, a `board` / a non-STM32F4 `device` / a PlatformIO-only action routes to PlatformIO; blank/F407 stays on the template MCP (zero regression). The newest silicon (STM32C0/H5/U0/WBA/N6) awaits the ST-native STM32CubeCLT backend (Phase 2/3) and is refused cleanly. **Zero-config**: STM32er DOWNLOADS and installs the MCP itself on first use (shallow `git clone`, or a GitHub-zip fallback when git is absent, then pip-installs `mcp`/`pyserial` if missing, then validates) into a per-user cache, so the user installs **only STM32CubeIDE + Tlamatini** — `action='bootstrap'` (re)provisions it explicitly. Before any compile/flash it runs a **safety preflight** that validates the arm-none-eabi-gcc toolchain / STM32CubeIDE / build tool / programmer / ST-LINK USB driver + a positively-confirmed connected probe / target device family, and **REFUSES (fail-safe)** rather than producing or uploading mis-targeted firmware — compile-only actions need NO board, but flash / erase / reset / serial / SWD / live-memory require a connected ST-LINK, and on the template-MCP backend a cross-family device is refused **and ROUTED to the PlatformIO backend** (whose own fail-safe preflight refuses only the newest silicon awaiting CubeCLT, flashes over the ST-LINK/SWD probe, and only WARNS on an inconclusive ST-LINK miss so a bare dongle is not false-refused); `action='validate'` reports the whole environment without building. On trigger it spawns that project's FastMCP **stdio** server (`mcp/stm32_mcp_server.py`), performs the MCP initialize handshake, and runs ONE capability selected by its `action` field, then captures the result into an `INI_SECTION_STM32ER` block (`action`, `tool`, `ok`, `returncode`, `success`, `project_dir`, `session_id`, `stage`, plus a `response_body` with the tool's stdout/stderr or JSON) so a downstream Forker can branch on `{success}` / `{returncode}` and Parametrizer can pipe `{project_dir}` (or live-memory samples) onward; it ALWAYS triggers `target_agents` (success or failure). The `action` covers all 23 MCP tools — environment (`get_config`, `discover_toolchain_tool`); project lifecycle (`create_project`, `write_source`, `read_source`, `list_sources`, `clean`); build & flash (`build`, `list_artifacts`, `flash`, `build_and_flash`, `erase`, `reset`); serial / VCP hardware-in-the-loop (`serial_list_ports`, `serial_connect`, `serial_send`, `serial_read`, `serial_disconnect`); and live SWD memory of a RUNNING target without halting it (`read_memory`, `write_memory`, `live_memory_start`, `live_memory_read`, `live_memory_stop`) — plus two composites that chain the stateful tools in one run: `serial_session` (connect → send/read → disconnect) and `live_monitor` (start → stream `monitor_seconds` → read → stop). A typical pipeline chains `create_project` → Parametrizer (carry `{project_dir}` forward) → `write_source` (drop generated `main.c`) → `build_and_flash` → a `live_monitor` / `serial_session` that proves the firmware runs on real silicon. Leave `server_script` **blank** for the zero-config auto-download (set it only to point at an existing local checkout — an on-disk path wins and skips the bootstrap); set `mcp_python` only if the Python running the server lacks the `mcp` / `pyserial` packages. On the canvas you set `stm32_backend` / `board` / `framework` / `environment` (PlatformIO) and `auto_bootstrap` / `mcp_repo_url` / `mcp_install_dir` / `preflight` / `device` in this node's dialog. In **chat (Multi-Turn)** you never repeat anything — Tlamatini auto-injects the **`stm32_mcp_server_script`** (default empty = bootstrap) plus optional `stm32_mcp_python` / `stm32_template_dir` / `stm32_ide_root` / `stm32_mcp_repo_url` / `stm32_mcp_install_dir`, **plus the SHARED `pio_executable` / `pio_core_dir`** (same globals as ESP32er), you set once in **Config ▸ URLs** on every `chat_agent_stm32er` run. Observational/output (mutates no persistent state), but it STILL appears in the Exec Report (2026-06-07: EVERY Multi-Turn agent does). **NOTE**: fetching the tokens needs only the stdlib, but rendering audible audio needs `snac` + `torch` (a neural vocoder) installed (`pip install snac torch`); without them Talker saves the audio tokens and reports `status: tokens_only`. The visual-canvas counterpart of the `chat_agent_talker` Multi-Turn tool. |
| **Mouser** | Mouse movement, clicks, drags, scrolling, window anchors, and reference-image matching. Explicit `coordinate_space` supports physical screen pixels, desktop offsets, window/client positions, normalized positions, and screenshot-to-screen mapping. Handles negative monitor origins, rejects monitor gaps, checks window focus/point ownership for targeted actions, and refuses ambiguous window/image matches. `movement_type: inspect` returns cursor and monitor geometry without input. Reports `action_status` and observed coordinates; input delivery is not application-outcome verification. Reserved for requested desktop UI work; use File-Creator, Executer, and Pythonxer for file/code tasks. |
| **Windower** | The window manager of the desktop-UI trio (Windower = the window itself, Mouser = clicks inside it, Keyboarder = typing into it). Locates an application window by title and runs ONE lifecycle operation on it — `focus`/raise, `minimize`, `maximize`, `restore`, `move`, `resize`, `move_resize`, `close`, `topmost`/`untopmost`, or `arrange` (snap/tile to a screen region) — or `list`s every open window with its position, size and state. Matching is by `substring` (default), `exact`, or `regex`, with `match_index` to pick among same-titled windows. Implemented self-contained with the Win32 API (pywin32), including the reliable cross-process focus-transfer (AttachThreadInput) ported from Microsoft's Windows-MCP. Emits an `INI_SECTION_WINDOWER` block (`action`, `window_title`, `matched`, `match_count`, `state`, `left`, `top`, `width`, `height`) so a downstream Forker can branch on `{matched}`/`{state}` and Parametrizer can pipe geometry onward; always triggers `target_agents`. **Use Windower — not Mouser — whenever the goal is the window as a whole (bring to front, tile, resize, close by title); Mouser only clicks controls inside a window.** The visual-canvas counterpart of the `chat_agent_windower` Multi-Turn tool. |
| **Keyboarder** | Checked Windows keyboard input, bound to one HWND/PID and stopped on foreground focus loss. Supports literal Unicode text (`input_mode: text`) including accents and emoji, plus the existing quoted-text/key/chord sequence syntax. Uses SendInput, checks inserted-event counts, releases owned modifiers on failure, and keeps the corner emergency stop enabled. Reports `action_status`, input counters, and target identity. Input delivery does not verify the focused field or its resulting content. Reserved for requested desktop UI work; use file/execution agents for authoring or running code. |

### Notification Agents

These are *terminal* agents — they react to upstream events but do NOT start anything else. Their job is to tell the outside world that something happened.

| Agent | Description |
|-------|-------------|
| **Notifier** | The browser-notification agent. Watches its `source_agents` for any of a comma-separated list of `search_strings` and, on a match, drops a `notification.json` file that the Tlamatini chat UI polls and renders as an in-browser DOM popup (with optional sound). Per-source file offsets and reanim files mean it never re-processes old log content even across restarts. |
| **Emailer** | Sends an SMTP email when triggered. Configurable sender, password, list of recipients, subject, and body. Common pattern: wire a Raiser to detect the success or failure of an upstream pipeline and have it trigger Emailer to notify a team mailing list. |
| **RecMailer** | An IMAP email receiver with LLM analysis. Polls a configured inbox, downloads new messages, and asks an Ollama model whether the body matches one of your `keywords_or_phrases`. Logs every match with the configured `outcome_word`. Use it to make a flow react to a real email arriving, e.g. an alert from an external SaaS. |
| **Whatsapper** | The single WhatsApp send/receive agent with two explicit outbound identities. Three `mode`s remain available: `send` (post a `message`/`template` then start `target_agents` and die), `receive` (listen on the official webhook for `rx_max_seconds`, then start `target_agents` and die), and auto (infer from config). Address the recipient by a `contact_name` resolved from the Contacts book (`contacts.json`, next to `config.json`) or by a literal `whatsapp.to` number. Pick WHICH NUMBER sends with `provider`: `cloud` (default) uses Meta's **official WhatsApp Cloud API** from the BUSINESS number, with System User, template, and 24-hour-window rules; `web` sends from YOUR OWN personal number by automating WhatsApp Web after a one-time QR login, with no templates or System User. Plain English works, so "send it as me" / "from my own WhatsApp" → `provider=web` and "as the business" / "official" → `provider=cloud`. The `web` route is UNOFFICIAL and can get a number Meta-banned; the `web:` config block (`headless` / `login_wait_seconds` / `settle_seconds` / `profile_dir`) tunes it and the QR login is remembered per install. It STARTS `target_agents` and is a Parametrizer source emitting `INI_SECTION_WHATSAPPER` (fields `mode`, `direction`, `recipient`, `status`, `message_id`; body = `response_body`). Handy as a "page my phone when the build breaks" channel or a webhook-driven inbound trigger. |
| **Telegrammer** | The single Telegram send/receive agent using official Telegram surfaces only. Bot mode uses the official Telegram **Bot API** (`telegram.bot_token` from @BotFather); optional user mode uses the official Telegram API session (`telegram.api_id`, `telegram.api_hash`, `telegram.session_name`/`session_string`) so private `@username` sends can stay human-readable in configs. Three `mode`s: `send` (post a `message` to a `telegram.chat_id`/`@username` or `contact_name`, then start `target_agents` and die), `receive` (listen for `rx_max_seconds`, optionally filtered by `rx_from_chat_id` / `rx_match`, then start `target_agents` and die), and auto (infer from config). Address the recipient by a `contact_name` resolved from `contacts.json`; that contact may keep `telegram: "@username"`. Telegrammer uses a local username cache plus official Bot API `getChat`/`getUpdates` lookup, and falls back to the official user-session API when configured. Pick WHICH IDENTITY sends with `provider`: `bot` sends AS the bot (Bot API), `user` sends AS your own logged-in account (user session, for private `@username` sends); plain English works, so "send it as me" → `provider=user` and "as the bot" → `provider=bot`, while `auto` (default) uses your account for private `@usernames`/`+phone` and the bot for numeric ids/channels. It STARTS `target_agents` and emits `INI_SECTION_TELEGRAMMER` (fields `mode`, `direction`, `chat_id`, `status`, `message_id`; body = `response_body`). |
| **Zavuerer** | Tlamatini's bridge to **Zavu** (https://www.zavu.dev) — ONE unified API for SMS, WhatsApp, Telegram, Email and Voice. Instead of separately wiring Twilio (SMS) + Meta's WhatsApp Cloud API + SMTP, Zavuerer sends through Zavu's single REST endpoint with one API key, optional ML smart-routing (`channel: auto`) and automatic channel fallback (e.g. WhatsApp fails → SMS). On trigger it runs ONE capability selected by its `action` field: `send` (POST a message — `to` a +E.164 phone for SMS/WhatsApp/Voice/Telegram or an email address for Email, `text`, `channel` ∈ `auto`/`sms`/`whatsapp`/`telegram`/`voice`/`email`, optional `subject`/`from_sender`/`fallback`) or `health` (probe the API and whether the key is configured). It captures the result into an `INI_SECTION_ZAVUERER` block (`action`, `channel`, `to`, `status`, `message_id`, `success`, `base_url`; body = `response_body`) so a downstream Forker can branch on `{success}` / `{status}` and Parametrizer can pipe the message id onward; it ALWAYS triggers `target_agents` (success or failure). The `zavu_api_key` is set once (get the key at https://www.zavu.dev — free to sign up, but Zavu charges pay-as-you-go per message sent) — if it is empty a `send` REFUSES with a one-line "set your Zavu key" message (status `refused`) instead of failing silently. Implemented self-contained with the Python stdlib (`urllib`), so it needs no SDK in the agent pool. **Authorized, opted-in recipients only — respect each channel's anti-spam / consent rules (A2P, the WhatsApp 24-hour window, GDPR).** The visual-canvas counterpart of the `chat_agent_zavuerer` Multi-Turn tool. |
| **Monitor-Log** | A pure log-file watcher with LLM event detection. Polls a configured `logfile_path`, feeds new lines to an Ollama model, and logs `outcome_word` (default `TARGET_FOUND`) when a match is detected. Designed to be the upstream `source_agents` of a Raiser — together they form the canonical "react to a log line" mini-flow. |
| **Monitor Netstat** | The network-port version of Monitor-Log. Polls the system's open TCP/UDP connections, feeds them to the LLM, and emits `TARGET_FOUND` when the configured network condition matches. Use it for "alert me if port X opens" or "fire when no connection to host Y exists for N seconds". |
| **FlowHypervisor** | Watches a running flow using process state, logs and current agent contracts. It distinguishes execution branches from Ender kill lists and log/data dependencies, includes configured desktop timing, and retains the latest mouse/keyboard receipts between log polls. It alerts on problems; input delivery is not treated as proof that an application was edited, saved or closed. |

### Utility Agents

Glue and infrastructure agents — they do not directly produce output but make the rest of the canvas easier to wire.

| Agent | Description |
|-------|-------------|
| **Parametrizer** | Carries structured results from one agent into another agent’s configuration, one segment at a time. Its parser registry follows all declared output producers (53 currently, including Keyboarder). It preserves empty fields, checks numeric and Boolean conversions, and requires every configured mapping to succeed before writing or starting the target. It backs up and restores the target config and blocks automatic replay of interrupted mouse/keyboard input until application state is checked. |
| **FlowBacker** | A passive backup utility. When triggered (typically by Ender), it copies the entire deployed session pool directory to a configured `target_directory`, overwriting any previous backup of the same session, then launches its `target_agents` (Cleaners). The "save before you wipe" step in any flow that ends with cleanup. |
| **FlowCreator** | Designs a workflow from your objective. It first selects from all 89 installed agent types, then uses their detailed instructions and current configuration/connection contracts to produce a .flw file. It checks references, branches, fields and Parametrizer mappings before publishing, with bounded repair for invalid plans. The generated flow remains reviewable before you run it; catalog coverage does not guarantee every external application or service is ready. |
| **Gatewayer** | The inbound gateway. A long-running agent that listens for external events on either an HTTP webhook (default `127.0.0.1:8787`) or a folder-drop watcher, normalizes each event into a canonical envelope, persists it to disk, and dispatches downstream agents serially. Supports bearer-token, HMAC, and IP-allowlist authentication, plus dedup, persistence, and crash recovery. The agent that lets the outside world *call into* a flow — webhooks, IoT pushes, SaaS callbacks, scheduled batch drops, all welcome. |
| **Gateway Relayer** | A deterministic, no-LLM relay that bridges third-party webhook formats (e.g. GitHub's `X-Hub-Signature-256`) into Gatewayer's expected `timestamp + body` HMAC scheme. Validates the upstream provider's signature, transforms the payload, signs it for Gatewayer, and forwards it. Use it whenever you want a flow to receive native GitHub / GitLab / Stripe / Shopify webhooks without patching Gatewayer itself. |
| **NodeManager** | A long-running infrastructure registry. Maintains a live inventory of local and remote nodes, probes each one's health (ping, TCP, SSH, WinRM, HTTP), classifies state (`ONLINE` / `OFFLINE` / `DEGRADED` / `UNKNOWN`), detects capability changes, persists state across restarts, exports filtered manifests on demand, and triggers `target_agents` on configured node events. The control-tower agent for fleets of machines. |

### Cryptography Agents

Post-quantum cryptography primitives, deterministic and short-running.

| Agent | Description |
|-------|-------------|
| **Kyber-KeyGen** | Generates a CRYSTALS-Kyber post-quantum public/private key pair in base64. Three variants are supported: `kyber-512`, `kyber-768` (default), and `kyber-1024`. Output is logged in a structured block so a downstream Parametrizer can route the keys directly into Kyber-Cipher and Kyber-DeCipher. |
| **Kyber-Cipher** | Encrypts a plaintext buffer with a CRYSTALS-Kyber public key. Internally uses Kyber **encapsulation** to derive a shared secret and AES-256-CTR to encrypt the buffer; the agent logs the encapsulation, IV, and cipher text in base64, all wired so they can be piped into Kyber-DeCipher by Parametrizer. |
| **Kyber-DeCipher** | The inverse of Kyber-Cipher. Decrypts a base64 cipher text using the matching CRYSTALS-Kyber **private key** plus the encapsulation and IV that Kyber-Cipher emitted. Emits the recovered plaintext into its log, ready for File-Creator or another consumer. |

## Notes on Maintenance

- **Adding a new agent**: append a new row to the relevant table above using the same Markdown format. The parser only requires `^\|\s*\*\*<Name>\*\*\s*\|\s*<description>\s*\|`. Section headings (`### ...`) are ignored by the parser; they exist purely for human readers.
- **Renaming an agent**: change the `**Name**` cell — but remember the lookup is normalized to lowercase alphanumeric, so `**Kyber-KeyGen**`, `**KyberKeyGen**`, and `**kyber keygen**` all hit the same slot. As long as your normalization matches the DB display name, the tooltip stays connected.
- **Frozen builds**: `build.py` copies this file into `dist/manage/agents_descriptions.md` so it ends up in the install directory next to `Tlamatini.exe`. The view loader probes `agents_descriptions.md` first, then falls back to `README.md` (so older deployments that haven't updated yet still work).
